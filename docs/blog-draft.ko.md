# "재현이 안 돼요"를 실패하는 테스트로: 세션 녹화로 버그를 재현하는 MCP를 만들며 배운 것

## 문제: 재현 절차가 없는 버그 리포트

프론트엔드 개발자라면 이런 리포트를 자주 받습니다. "결제하다가 화면이 멈췄어요." 재현 절차는 없고, 따라 해 보면 멀쩡합니다.

세션 녹화(rrweb 같은)가 있으면 사용자가 한 일을 볼 수는 있습니다. 그래도 녹화를 보는 것과 버그를 재현하는 건 다른 일입니다. 저는 코딩 에이전트가 녹화를 받아서 **그 버그로 실패하는 테스트**를 만들고, 그 테스트가 통과할 때까지 코드를 고치게 하고 싶었습니다. 그래서 MCP 서버 bugprint를 만들었습니다.

## 녹화를 테스트로 바꾸는 건 쉬운 부분이었다

처음에는 녹화된 클릭과 입력을 테스트 코드로 옮기면 끝날 줄 알았습니다. 실제로 그 부분은 비교적 금방 됐고, 비슷한 일을 하는 도구도 이미 있었습니다. 어려운 건 그다음이었습니다.

- 사용자가 받은 API 응답이 지금은 다르면, 같은 단계를 실행해도 버그가 나지 않습니다.
- 테스트가 실패해도, 버그 때문이 아니라 버튼 이름이 바뀌어서 실패한 것일 수 있습니다.
- 녹화가 13단계라도 버그에 필요한 건 그중 몇 개뿐입니다.

그래서 bugprint는 테스트를 "만드는" 것보다 테스트가 "정말로 재현하는지"에 집중했습니다.

## 1. 클릭한 요소를 사람이 읽을 수 있는 로케이터로

rrweb은 "노드 #57을 클릭했다"고만 기록합니다. 그래서 스냅샷과 이후 DOM 변경을 재생해 가상 DOM을 만들고, 클릭한 순간 그 노드가 어떤 모습이었는지 복원했습니다. 그다음 testid → label → role+name 순으로 로케이터 후보를 만들고, 녹화된 DOM에서 정확히 하나만 가리키는 후보를 고릅니다. "Add to cart" 버튼이 여러 개면 `getByRole('listitem').filter(...)`처럼 가까운 컨테이너로 범위를 좁힙니다.

여기서 배운 점이 있습니다. **내가 만든 매칭 로직이 내 로케이터를 맞다고 하는 건 증거가 되지 않습니다.** 실제 브라우저에서 녹화한 뒤, 생성한 로케이터를 실제 test runner로 풀어 보는 테스트를 추가했더니 두 가지가 바로 드러났습니다.

- 표의 행 이름을 저는 `AliceEdit`으로 계산했는데, 브라우저는 `Alice Edit`이었습니다. 블록과 셀 경계에는 공백이 들어갑니다.
- `hasText: 'Product 1'`은 부분 일치라서 `Product 10`에도 걸렸습니다. 그래서 제목을 정확히 일치시키는 `filter({ has: heading })`으로 바꿨습니다.

## 2. 클릭만이 아니라 환경도 재생하기

데모의 버그는 쿠폰 API가 만료된 쿠폰에 `{ expired: true, discount: null }`를 200으로 돌려주는데, 클라이언트가 `res.ok`만 보고 넘어가서 결제 때 크래시가 나는 경우입니다. 개발 환경에서는 쿠폰이 유효해서 손으로는 재현되지 않습니다.

bugprint는 녹화된 응답을 테스트 안에서 `page.route`로 돌려주고, 시계를 녹화 시점에 맞춥니다.

|                      | 결과                             |
| -------------------- | -------------------------------- |
| 녹화된 응답으로 실행 | 🐞 reproduced                    |
| 실제 API로 실행      | ✅ passed (버그가 나타나지 않음) |
| 수정 후 실행         | ✅ passed                        |

두 번째 줄이 이 프로젝트를 만든 이유입니다.

녹화된 응답에는 토큰이 들어 있을 수 있고, 생성된 테스트는 git에 커밋됩니다. 그래서 키 이름을 단어 단위로 나눠서(`accessToken` → access, token) 민감한 값을 가렸습니다. 그냥 `/auth/`로 찾으면 `author`까지 걸리기 때문입니다.

## 3. "실패했다"가 아니라 "같은 이유로 실패했다"

`run_and_verify`는 테스트를 실행하고 `reproduced` / `failed-differently` / `passed`로 판정합니다. 판정이 `failed-differently`면, 실패한 줄을 단계 id로 되짚어서 "s11 Apply 클릭에서 실패" 같은 정보를 함께 줍니다. 에이전트는 이걸 보고 앱이 아니라 테스트를 먼저 고칩니다.

이 부분에서 가장 기억에 남는 버그가 나왔습니다. 축소 기능을 만들고 처음 돌렸더니 결과가 "페이지 열기 + Apply 클릭" 2단계였습니다. 쿠폰 코드도 넣지 않고 주문도 하지 않았는데 크래시가 재현됐다는 뜻이라 말이 안 됐습니다. 원인은 verify였습니다. 실패 메시지에는 코드 일부가 같이 찍히는데, 생성된 테스트의 주석에 녹화된 에러 문구가 적혀 있어서, 상관없는 404 에러로 실패해도 메시지 안에서 그 문구가 발견된 겁니다. 지금은 테스트가 실제로 잡은 에러를 annotation으로 넘기고, 그것끼리만 비교합니다.

**한 기능(축소)이 다른 기능(검증)의 버그를 드러냈다**는 점에서, 기능을 서로 엮어 두는 게 테스트 역할도 한다는 걸 배웠습니다.

## 4. delta debugging으로 원인 단계만 남기기

`minimize_repro`는 먼저 중간 페이지를 바로 열어도 재현되는지 보고, 그다음 delta debugging(ddmin)으로 단계를 지웁니다. 테스트를 수십 번 돌려야 하는데, 후보마다 앱 서버를 띄우면 너무 느립니다. 그래서 라운드마다 후보를 모두 파일로 쓰고 한 번의 실행에서 병렬로 돌렸습니다.

결과: **13단계 → 4단계, 8라운드, 26번 실행, 약 18초.** 남은 4단계(결제 페이지 열기 → 쿠폰 입력 → Apply → 주문)가 원인을 그대로 가리킵니다.

## 5. 실제 에이전트에게 맡겨 보기

마지막으로 헤드리스 Claude Code에 bugprint만 연결하고 "결제가 크래시 난다, 녹화는 recording.json"이라고만 알려줬습니다. 에이전트는 17턴, 67초, 약 $0.40으로 재현 → 수정 → 확인까지 혼자 마쳤고, 고친 코드도 맞았습니다.

여기서도 버그가 하나 나왔습니다. 에이전트가 "주문 완료 문구가 보여야 한다"는 확인을 추가했는데, 이 확인이 에러 확인보다 먼저 실행돼서 크래시가 시간 초과로 가려졌습니다. 에이전트는 테스트를 직접 고쳐서 넘어갔지만, 원래 도구가 해 줬어야 하는 일이라 확인 순서를 바꿨습니다.

## 돌아보며

- 테스트 코드를 만드는 것보다, 그 테스트가 무엇을 증명하는지 확인하는 데 시간이 더 들었습니다.
- 혼자 짠 로직이 혼자 맞다고 하는 테스트는 믿기 어렵습니다. 실제 브라우저, 실제 runner, 실제 에이전트로 확인할 때마다 버그가 하나씩 나왔습니다.
- 에이전트용 도구는 출력이 짧고, 다음에 할 일이 분명해야 합니다. 판정과 실패한 단계 id가 그 역할을 합니다.
